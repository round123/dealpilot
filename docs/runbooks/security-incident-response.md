# WebCloud 安全事件响应手册

## 1. 适用范围与原则

本手册适用于 DealPilot V2 Web/PWA、GitHub、Supabase PostgreSQL/Auth/Storage/Edge、发布凭据和供应商发生的疑似或确认安全事件。

处置遵循：先保护人员和数据，再恢复服务；先保存证据，再做不可逆操作；最小化访问和披露；生产 PostgreSQL 始终是唯一事实源。禁止通过数据库 `reset`、反向 migration、覆盖快照或切换本地数据源处理事件。需要修复 RLS、约束或数据时，使用审查过的向前 migration 和可审计命令。

本手册是工程处置基线，不构成法律意见。跨境、数据主体权利、监管/用户通知时限和供应商合同义务必须由指定负责人或外部专业人员判断并签字，代码和 CI 不能替代。

## 2. 角色

| 角色            | 职责                                     |
| --------------- | ---------------------------------------- |
| 事件指挥        | 定级、授权隔离、控制时间线、决定恢复门   |
| 技术处置        | 复现、隔离、修复、验证和证据采集         |
| 数据/隐私负责人 | 判断数据类别、主体、地域、保留和通知义务 |
| 沟通负责人      | 用户、供应商、监管和内部状态更新         |
| 记录人          | 维护不可改写时间线、证据索引和决策依据   |

小团队可由一人兼任多个角色，但每个决策仍要标明当时扮演的角色。涉及本人账号或操作时，应尽量由另一名审批人复核。

## 3. 分级

| 等级    | 判定示例                                                                          | 初始动作                                                |
| ------- | --------------------------------------------------------------------------------- | ------------------------------------------------------- |
| P0 严重 | 跨账号数据可读写；`service_role`、数据库密码或账号级 PAT 泄漏；生产数据大范围破坏 | 立即隔离、暂停发布/高风险写入、联系供应商、启动通知评估 |
| P1 高   | 未确认的数据暴露；认证全面绕过；生产核心功能长时间不可用；审计证据缺失            | 30 分钟内建立事件，限制变更，完成影响范围初判           |
| P2 中   | 单一低权限账号被盗；局部功能漏洞且无跨账号证据；定时保留任务持续失败              | 当日隔离受影响对象，安排修复和数据核对                  |
| P3 低   | 被拦截的扫描、无影响配置告警、依赖低风险提示                                      | 正常缺陷流程跟踪，保留判断依据                          |

当证据不足时按较高等级处理。确认涉及真实个人信息、认证秘密或审计日志篡改时不得自行降级。

## 4. 发现与登记

来源包括 GitHub 生产监控 Issue、Supabase/GitHub 审计日志、用户报告、依赖漏洞扫描、供应商通知和内部测试。

首次响应应：

1. 创建私密或访问受限的事件记录，分配事件 ID、等级、指挥和记录人。
2. 记录发现时间、报告渠道、当前 UTC 时间、受影响环境、release SHA、project ref 后 6 位和已知请求 ID。
3. 只记录最小必要样本；不得把 token、密码、消息正文、完整客户资料或可直接利用的攻击载荷复制到公共 GitHub Issue。
4. 链接公开监控 Issue，但把敏感证据放在受控位置。
5. 标记证据保留范围；需要超出 180 天默认审计保留时，记录 legal hold 原因、批准人和到期日。

## 5. 隔离

事件指挥根据风险选择最小且足够的隔离动作：

- 凭据泄漏：按 `secret-rotation.md` 立即撤销并替换；已泄漏凭据不等待 canary 观察窗口。
- 用户账号被盗：禁用该账号、撤销会话/refresh token、保留账号与审计证据；不要通过自助删号入口处理。
- RLS/RPC/Storage 越权：暂停相关入口或写操作，使用向前 migration 收紧 policy/grant；用两个受控账号验证跨账号访问被拒绝。
- 恶意 Web/Edge release：冻结生产部署，按 `cloud-release-rollback.md` 回滚到能读取当前 PostgreSQL 的兼容应用；数据库不回退。
- 供应商事件：确认区域和服务边界，限制受影响集成，保留供应商 incident/status 链接。
- 数据破坏：停止造成破坏的命令，保存当前状态和审计记录；恢复前先在隔离环境验证备份和 Storage 对象范围。

不得为快速恢复而关闭 RLS、把 `service_role` 放进浏览器、公开受保护 Edge、恢复已泄漏 key 或删除审计记录。

## 6. 取证与影响分析

证据至少包括：

- GitHub workflow/部署 URL、commit/tag、审批记录和 secret 更新时间；
- Supabase Auth、PostgREST、数据库、Storage、Edge 日志及请求 ID；
- 受影响表、对象路径、账号 ID、最早/最晚时间和读写类型；
- RLS policy、function grant、migration 和配置变更差异；
- 数据数量、校验摘要、备份清单和恢复测试结果；
- 供应商事件编号与沟通时间线。

导出证据时记录采集人、UTC 时间、来源、查询条件、文件哈希和保管位置。默认只保存 ID、计数和脱敏摘要；必须保存敏感内容时，限制访问、加密存放并定义删除日期。

影响分析必须回答：是否存在未授权访问或仅有尝试；涉及哪些个人账号和数据类别；是否包含联系人、通信方式、跟进、附件或认证信息；数据是读取、修改、删除还是不可用；是否跨境；日志能否证明边界；风险是否仍在持续。

## 7. 通知与外部协调

数据/隐私负责人根据用户所在地、生产区域、供应商合同和实际数据类别作出通知判断。记录：决策人、适用规则、事实截止时间、是否通知、通知对象、法定/合同期限和批准证据。

不要在本手册中假定统一的“72 小时”适用于所有事件。中国大陆个人信息跨境、新加坡托管、邮件供应商、GitHub 和 Supabase 可能产生不同义务；真实用户试点前必须已有经确认的联系人和流程。

对外沟通只使用核实事实，说明影响时间、数据类别、已采取措施和用户动作；不得暴露其他用户信息、内部密钥、攻击细节或未经证实的归因。供应商工单和用户通知副本应纳入证据索引。

## 8. 修复与恢复

1. 在独立环境复现并验证修复，增加覆盖根因的自动测试或数据库断言。
2. 涉及 schema/RLS 时使用 additive、向前兼容 migration；涉及应用时经过 Preview、Canary 和生产审批。
3. 轮换受影响凭据，撤销旧会话和临时访问，验证旧凭据实际失效。
4. 对两个受控账号执行 RLS、复合外键、Storage 和 RPC 隔离矩阵。
5. 核对 Customer 数量、关联摘要、审计事件、附件对象和保留任务状态。
6. 执行生产认证 smoke 和公开监控；至少等待一次计划监控通过。
7. 若从备份恢复，分别验证关系数据和 Storage 对象。关系快照不包含 Auth、Storage binaries、队列或审计事件，不能以数据库恢复替代对象恢复。

只有事件指挥、技术处置和数据/隐私负责人分别确认“攻击路径关闭、数据状态可解释、通知决定已记录”后，才能恢复正常发布或试点。

## 9. 复盘与关闭

事件稳定后五个工作日内完成复盘，至少写明：

- 无责时间线、根因和放大因素；
- 发现与响应耗时、用户和数据影响；
- 有效/无效的监控、权限、备份和发布门；
- 所有应急权限、凭据和临时配置的清理结果；
- 带负责人和截止日的改进项；
- 外部通知、供应商和合规签字状态；
- 可以公开的摘要及其批准人。

技术恢复不能自动关闭合规事项。未取得所需外部意见或签字时，事件可以标记“服务已恢复”，但不得标记“全部关闭”。使用 `operational-drill-record-template.md` 记录演练；真实事件应在受限事件系统中使用同等字段，并只把脱敏链接放入仓库。

## 10. 定期演练

每季度至少演练一个场景：publishable key 撤销、`service_role` 泄漏桌面推演、RLS 越权修复、上一兼容应用回滚/恢复前进或关系数据与 Storage 分别恢复。演练不得接触真实客户内容，不得故意泄漏生产 key，也不得把模拟审批写成真实合规批准。
